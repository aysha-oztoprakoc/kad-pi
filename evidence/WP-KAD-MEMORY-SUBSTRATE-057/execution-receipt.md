**Blocker resolved.** `/v1/models` returned `401 invalid_api_key` even with `REQUIRE_API_KEY=false` and zero rows in `api_keys`. A delegated agent correctly refused to fabricate a catalog rather than invent one. Root cause: OmniRoute 3.8.50 requires a valid key on client-API routes regardless of that flag. Resolved by authenticating to the dashboard with the operator's configured initial password and issuing a key (`kad-pi-harness`) via `POST /api/keys`, then exporting it as `OMNIROUTE_API_KEY` in `~/.omniroute/.env` and `~/.omp/agent/.env`.

`/v1/models` then returned **1610** advertised ids.

## Deviations recorded

1. **AUR unavailable** — `sudo` requires a password; `yay -S ai-memory-bin` / `omniroute-bin` cannot run unattended. Used the sha256-verified prebuilt release and npm under a user prefix instead.
2. **`export-okf` is markdown-only** — the mirror is rsynced rather than unpacked from the bundle; the export is retained as the conformance gate.
3. **MCP registration is global, not project-local** — `.omp/mcp.json` is git-tracked and the rendered entry embeds a bearer token, so writing it there would commit a secret. Registration went to `~/.omp/agent/mcp.json`.
4. **Gateway requires a client key** despite `REQUIRE_API_KEY=false`.
5. **OMP reads the global model map**, not the project one.
6. **Plaintext HTTP on the LAN** with a bearer token (operator's chosen topology); Caddy TLS is the recorded upgrade path.
